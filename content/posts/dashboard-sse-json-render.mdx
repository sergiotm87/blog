## Why fetch() Instead of EventSource

The browser's `EventSource` API is purpose-built for SSE, but it has a critical limitation: no support for custom request headers. Since the API authenticates via `Authorization: Bearer <JWT>`, using `EventSource` would require passing the token as a URL query parameter:

```
// Bad: JWT leaked in URL
new EventSource("/api/v1/stream?token=eyJhb...")
```

This token would appear in server logs, proxy logs, browser history, and any monitoring tool. Instead, I use `fetch()` with `ReadableStream`:

```typescript
const response = await fetch(url, {
  headers: { Authorization: `Bearer ${token}` },
});
const reader = response.body!.getReader();
```

The tradeoff: I lose `EventSource`'s built-in reconnection and must implement it myself. Given the security benefit, this is a clear win.

## The useEventStream Hook

The hook manages the SSE connection lifecycle:

```typescript
export function useEventStream(endpoint = "/api/v1/stream") {
  const { getToken } = useAuthContext();
  const [spec, setSpec] = useState<Spec | null>(null);
  const [connectionState, setConnectionState] = useState<ConnectionState>("closed");
  // ...
}
```

### Connection Flow

1. **Get token**: Call `getToken()` from the auth context (Clerk in production, mock in development)
2. **Open connection**: `fetch()` with `Authorization` header and `Accept: text/event-stream`
3. **Read stream**: `response.body.getReader()` returns a `ReadableStreamDefaultReader`
4. **Parse frames**: Accumulate text in a buffer, split on `\n\n`, parse each frame's `event:`, `id:`, and `data:` fields
5. **Apply events**: Route to the appropriate handler based on event type

### SSE Frame Parsing

SSE frames are delimited by double newlines. Since `ReadableStream` chunks don't respect frame boundaries, I buffer incoming text and split:

```typescript
let buffer = "";

while (true) {
  const { done, value } = await reader.read();
  if (done) break;

  buffer += decoder.decode(value, { stream: true });

  const frames = buffer.split("\n\n");
  buffer = frames.pop() || ""; // Keep last incomplete frame

  for (const frame of frames) {
    const parsed = parseSSEFrame(frame);
    // Handle event...
  }
}
```

The `{ stream: true }` option on `TextDecoder` handles multi-byte characters that might be split across chunks.

### Event Handling

```typescript
switch (parsed.event) {
  case "spec-init":
    // Full spec replacement — initial state on connect/reconnect
    setSpec(JSON.parse(parsed.data));
    break;

  case "spec-patch":
    // Incremental update — array of RFC 6902 patches
    const patches: JsonPatch[] = JSON.parse(parsed.data);
    setSpec(prev => {
      if (!prev) return prev;
      return patches.reduce(
        (s, p) => applySpecPatch(s, p),
        { ...prev }
      );
    });
    break;

  case "heartbeat":
    // No-op — server sends every 15s to keep connection alive
    break;
}
```

<Callout type="info">
`applySpecPatch` from `@json-render/core` handles RFC 6902 operations (add, remove, replace, move, copy, test) on the json-render Spec structure. The spread `{...prev}` ensures immutability for React state updates.
</Callout>

## Exponential Backoff Reconnection

When the connection drops (network error, server restart, timeout), the hook reconnects with exponential backoff:

```typescript
const INITIAL_DELAY = 1_000;  // 1 second
const MAX_DELAY = 30_000;     // 30 seconds

// On error:
const jitter = Math.random() * 1000;
const delay = Math.min(reconnectDelay.current + jitter, MAX_DELAY);
reconnectDelay.current = Math.min(reconnectDelay.current * 2, MAX_DELAY);

setTimeout(() => connect(), delay);
```

Key properties:
- **Jitter** prevents thundering herd when many clients reconnect simultaneously
- **Max delay** caps the backoff at 30 seconds for reasonable UX
- **Reset on success**: When a connection opens successfully, the delay resets to 1 second
- **Last-Event-ID**: Sent as a header on reconnect for potential server-side resumption

type ConnectionState = "connecting" | "open" | "reconnecting" | "closed";

## Connection State in the UI

The `useEventStream` hook exposes `connectionState` for UI feedback. The charts page uses this to show contextual loading states:

```tsx
const { spec, connectionState } = useEventStream();

if (!spec) {
  return connectionState === "connecting" || connectionState === "reconnecting"
    ? "Connecting to event stream..."
    : "No events yet";
}
```

On connect, the server sends an empty feed spec (`spec-init`). The client accumulates patches from that point forward. On reconnect, the client starts fresh — for a real-time activity feed, this is the expected behavior.

## json-render Rendering

The rendering setup is straightforward. The registry defines available components (from `@json-render/shadcn`), and the provider + renderer handle the spec:

```tsx
// registry.ts
import { defineRegistry } from "@json-render/react";
import { shadcnComponents, shadcnComponentDefinitions } from "@json-render/shadcn";

const catalog = { components: shadcnComponentDefinitions };
export const { registry } = defineRegistry(catalog, {
  components: shadcnComponents,
});

// charts/page.tsx
<JSONUIProvider registry={registry}>
  <Renderer spec={spec} registry={registry} />
</JSONUIProvider>
```

The spec structure defines a `Stack` root with `Card` children. Each card represents an event (pattern created, target executed, workflow progress). The server controls what components are rendered, and the dashboard just renders whatever spec it receives.

### What a Spec Looks Like

To make this concrete, here's the exact `Spec` JSON that a "pattern created" event produces. The Go mapper builds this via JSON Patches, but the end result is a tree of elements keyed by ID:

```json
{
  "root": "event-feed",
  "elements": {
    "event-feed": {
      "type": "Stack",
      "props": { "gap": "md" },
      "children": ["evt-pattern-created-abc-1710000000"]
    },
    "evt-pattern-created-abc-1710000000": {
      "type": "Card",
      "props": {
        "title": "Pattern Created: BTCUSDT",
        "description": "headandshoulders on 1h"
      },
      "children": ["evt-pattern-created-abc-1710000000-time"]
    },
    "evt-pattern-created-abc-1710000000-time": {
      "type": "Text",
      "props": { "text": "2026-03-10T12:00:00Z" }
    }
  }
}
```

The `Renderer` walks this tree starting from `root`, looks up each `type` in the registry (`Stack` → shadcn Stack, `Card` → shadcn Card, etc.), and renders the React component with the given `props` and `children`. No client-side logic decides what to render — the server owns the UI structure entirely.

For workflow progress events, the child element uses a `Progress` bar instead of `Text`:

```json
{
  "evt-workflow-stu-bootstrap_targets-progress": {
    "type": "Progress",
    "props": { "value": 50 }
  }
}
```

As more events arrive, the server sends `spec-patch` frames that prepend new card keys to `event-feed.children` at index 0 (newest first), building up the feed incrementally.

## Decision UI (Future)

Decision events will render as special cards with action buttons and a countdown timer. The `respondToDecision` function sends the user's choice to the REST endpoint:

```typescript
const respondToDecision = async (decisionId: string, action: string) => {
  await fetch(`${baseUrl}/api/v1/stream/decisions/${decisionId}/respond`, {
    method: "POST",
    headers: {
      Authorization: `Bearer ${token}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ action }),
  });
};
```

The server then publishes resolution patches that remove the decision card and add a resolution card.

## Cleanup and Memory

The hook uses `AbortController` for clean teardown:

```typescript
useEffect(() => {
  mountedRef.current = true;
  connect();

  return () => {
    mountedRef.current = false;
    abortRef.current?.abort();  // Cancel in-flight fetch
  };
}, [connect]);
```

The `mountedRef` guard prevents state updates on unmounted components, and `AbortController.abort()` terminates the fetch stream immediately.
