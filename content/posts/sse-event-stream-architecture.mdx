## The Problem: Dashboard Fragmentation

Picture this workflow: a notification arrives saying a target was executed. You navigate to the patterns page, scroll through the list, find the right pattern, click it, see the state has changed, then navigate to the chart view to understand the context. By the time you arrive, new events have already happened.

This fragmented experience is common in data-intensive dashboards. Real-time context is scattered across notifications, lists, detail pages, and chart views. Each navigation breaks the mental model, and by the time you reconstruct the picture, it's stale.

We needed a unified, real-time view that shows system activity as it happens — no navigation required.

## Requirements

We defined five core requirements for the solution:

1. **Live contextual feed**: Events appear as they happen, rendered as structured UI cards (not raw JSON or log lines)
2. **Interactive decision points**: Some events require user action within a timeout window (approve, reject, skip) — with a countdown and default fallback
3. **Workflow progress visibility**: Multi-step backend operations (saga workflows with 4+ steps) should show real-time progress bars
4. **Reconnection resilience**: Clients that disconnect must receive the full current state on reconnect, not a replay of all historical events
5. **Per-user isolation**: Each user sees only their own events, routed by pattern ownership

## Why SSE Over WebSocket

We evaluated three approaches:

| Approach | Pros | Cons |
|----------|------|------|
| WebSocket | Bidirectional, low latency | Complex proxy config, no auto-reconnect, custom protocol |
| SSE (EventSource) | Standard protocol, auto-reconnect | No custom headers (JWT must go in URL) |
| SSE (fetch-based) | Standard protocol, custom headers, proxy-friendly | Requires manual reconnection logic |

We chose **fetch-based SSE**. The event stream is fundamentally unidirectional (server → client), which matches SSE's design. The fetch approach lets us send the JWT in the `Authorization` header instead of leaking it in URL query parameters. And unlike WebSocket, SSE works naturally through HTTP proxies, load balancers, and CDNs.

<Callout type="info">
The only user-to-server interaction (decision responses) uses a standard REST endpoint, not the SSE channel. This keeps the stream strictly unidirectional.
</Callout>

## The Architecture

The solution has four layers, each with a single responsibility:

```
Domain Events (NATS global topics)
    │
EventBridgeHandler (transforms + routes)
    │
Per-User NATS Subjects (buffers + isolates)
    │
SSE Handler → Dashboard (delivers + renders)
```

### Layer 1: Domain Events

The Go core already publishes events to global NATS topics via Watermill when patterns are created, states change, targets execute, etc. These events exist independently of the streaming feature.

### Layer 2: EventBridgeHandler

A new Watermill consumer subscribes to all domain topics. For each event, it:
- Resolves which user owns the event (via pattern → user_id)
- Transforms the event into RFC 6902 JSON Patches targeting a json-render spec
- Accumulates the patches into a per-user spec stored in NATS KV
- Publishes the raw patches to a per-user NATS subject

### Layer 3: Per-User NATS Subjects

Each user has a dedicated subject (`kajuna.user.<userID>.events`). NATS buffers messages even when no SSE connection is active, ensuring no events are lost during brief disconnects.

### Layer 4: SSE Handler + Dashboard

The Echo HTTP handler serves `GET /api/v1/stream`. On connect, it sends the full accumulated spec (`spec-init`), then forwards NATS messages as SSE events (`spec-patch`). The dashboard's `useEventStream` hook applies patches incrementally via `applySpecPatch` from `@json-render/core`.

## Why Server-Side UI Spec Generation

A key design decision: the server generates json-render specs and patches, not raw data. The dashboard renders whatever spec it receives.

This means:
- **No client deploys for UI changes**: Modify the spec mapper on the server, and all connected clients see the new UI immediately
- **Thin client**: The dashboard doesn't need to know about event types or how to render them
- **A/B testing**: Different users can receive different spec structures from the same event
- **Consistency**: The UI structure is defined in one place, regardless of how many clients consume it

## State Accumulation vs. Event Replay

A common pattern for event streaming is to replay all events on reconnect. We chose **state accumulation** instead: the server maintains the current spec in NATS KV, and reconnecting clients receive only the latest state.

This avoids:
- Ordering bugs from out-of-sequence replays
- Growing reconnection payloads as event history accumulates
- Client-side deduplication logic
- Stale UI from slow replays

The tradeoff is that NATS KV must be updated on every event (with CAS to avoid conflicts), but NATS KV is designed for exactly this kind of high-frequency key-value update.
